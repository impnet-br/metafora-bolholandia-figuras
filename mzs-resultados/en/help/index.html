How to submit your project

SZM Challenge · step by step

Português

This page describes the whole path, from the bench to the published result. The challenge statement, with the assembly requirements and the refutation criteria, is in the appendix on the Successive Zooms Method, in volume III of The Bubbleland Metaphor. Where the two disagree, the printed statement prevails.

  1. Before you power up the bench

    Check the assembly requirements in the statement, above all the three independent monitors: individual shielding, galvanic ground isolation, separate supplies and independent voltage references. Monitors sharing a reference produce the unanimous error — three identical readings, all wrong — which a majority of three cannot detect.

    And the rule that invalidates everything if broken: the value of √2 must not appear anywhere in the control loop, not in a debug assertion, not as a search seed. A forgotten sqrt(2.0) turns the demonstration into a tautology, however honest the intent.

  2. During the run: what to log

    Write a CSV with one row per stage. These are the columns the verifier reads and the assessment uses:

    ColumnContent
    stagestage index, starting at 1
    digitthe block of digits recovered at this stage
    trialshow many acquisition attempts the stage required
    monitor_a/b/cthe reading of each of the three monitors
    quantitythe physical quantity actually measured, and its order of magnitude
    temp_cambient temperature
    vref_vmeasured reference voltage

    The trials column is not a formality. A purely digital algorithm must search for each digit, testing candidates; the SZM reads it off an instrument. The number of attempts per stage is the observable that tells the two apart, and it is what defends the submission against the claim that the result is multiple precision in disguise.

  3. The control run

    Run the session a second time, with a single change: replace the analog reading with a random value, leaving the rest of the firmware untouched. Log it separately.

    This is mandatory. If the digit chain survives the noise, the analog block was not contributing, and the submission does not demonstrate the method — however many digits it shows. If it breaks at the first stage, as expected, the need for the analog reading is demonstrated by its absence.

  4. Check it yourself before sending

    Download the verifier and run it on both logs:

    python verificar.py log_estagios.csv    # your correct digits
python verificar.py log_controle.csv    # must BREAK early

    The verifier uses only the Python standard library — nothing to install. It is at verificar.py, and there is a complete example submission to compare your file formats against.

  5. Publish in your own repository

    The material stays in your public repository, under version control. It is not hosted here: copyright remains entirely yours, and version history is what distinguishes the firmware that produced the log from one adjusted afterwards. It must contain:

    • the firmware actually executed, with its version identified
    • a legible schematic and a photograph of the build
    • a component list with manufacturer, model and batch
    • both raw logs — session and control run
    • the calibration procedure used and the ambient conditions
    • an account of failures and intermediate adjustments

    The last item is asked for explicitly: calibrating the analog settling time is the most frequent failure mode, and the account spares whoever comes next. The general criterion is that a third party should be able to rebuild the setup without consulting you.

  6. Send the address

    Write to contato@impnet.com.br. Do not attach files: what you send is the repository address.

    Subject: SZM Challenge — submission

Repository: https://github.com/....
Correct digits: ...
Breaking stage: ...
Control run: broke at stage ...
Monitor correlation ρ: ...

  7. What happens next

    The logs are checked with the same verifier, and the material is read to judge whether independent reconstruction is possible. The control run is checked alongside: without it, or with it surviving the noise, the submission is not published as a result.

    Once accepted, a row is added to the results table, linking to your repository. Negative results are equally publishable: a submission that rigorously documents failure at a given stage, identifying the physical cause, is worth more than one claiming a high digit count without thermal records and without logs from the three monitors.
